# 可行性报告：移动端开屏广告拦截

> 结论先行：**Android 可以做出日常可用的 MVP；iOS 的天花板是「系统级 DNS 过滤」，无法做到系统级拦截。**

## 0. 一个必须先纠正的认知

开屏广告不是"一张图片"，是一条**网络请求链路**：

```
冷启动 App → 广告 SDK 请求广告(域名解析 + HTTPS) → 拉素材/曝光上报 → 倒计时 3-5s → 进主界面
```

我们做的是**让广告请求失败**，而不是"把广告滑走"。绝大多数 SDK 拿不到响应会直接跳过开屏、
进入主界面（个别会留 0.5-1s 兜底页）。这决定了技术方案必然落在下面三个合法通道之一：

| 通道 | 能力 | 本方案是否使用 |
|---|---|---|
| 网络层（VpnService / DNS 配置） | 让域名解析不出来 | ✅ 主通道 |
| UI 层（AccessibilityService） | 点用户本来能点的「跳过」 | ✅ 可选辅助 |
| 解析层（系统 DoT/DoH 设置） | 换一个过滤解析器 | ✅ 零成本兜底 |

**HTTPS 中间人改包这条路不通**：Android targetSdk≥24 不信任用户安装的 CA，
大厂 App 普遍证书固定（pinning），iOS 有 ATS。不要在这上面浪费时间。

## 1. Android：能做什么

| 能力 | 实现机制 | 真实边界 |
|---|---|---|
| 系统级 DNS 拦截 | `VpnService` 建立 tun，**只把 DNS 目标地址路由进隧道**（`addRoute` 只加解析器 IP），其余流量走物理网卡 | 只有 DNS 报文进 App，耗电接近 0，不降低网速 |
| 分应用代理 | `addAllowedApplication` / `addDisallowedApplication` | 精确到包名，同一条隧道不能混用两种 API |
| 无 root 常驻 | VPN 授权一次即可，配合系统「始终开启 VPN」 | 状态栏会常驻钥匙图标，这是系统行为，去掉不了 |
| 界面层点「跳过」 | `AccessibilityService` 读 View 树 + `ACTION_CLICK` | 需要用户手动开启无障碍，属敏感权限 |
| 零功耗兜底 | 系统「私有 DNS」(DoT, Android 9+) | 规则在远端、不能分应用、要信任解析器方 |

## 2. Android：做不到什么（全部是硬限制）

| 做不到 | 原因 |
|---|---|
| 读/改 HTTPS 内容 | targetSdk≥24 起系统不信任用户 CA；大厂 App 证书固定 |
| 拦 HTTPDNS / DoH | 阿里云 HTTPDNS、腾讯 DNSPod HTTPDNS 用「IP + 加密查询」直接绕过系统解析器。**这是国内覆盖率的最大杀手** |
| 拦已缓存素材 | 部分 SDK 预缓存开屏素材到本地，不走网络也能展示 |
| 拦 OpenGL/SurfaceView 自绘开屏 | 无障碍拿不到节点树，游戏类基本无效 |
| 在别人进程里挂钩 | 属 Xposed/LSPosed 领域，需要 root 或免 root 框架，超出「不 root」约束 |
| 拦开屏后信息流里的原生广告 | 那些是 HTTPS 内容流的一部分，DNS 层无法区分 |

## 3. iOS：能做什么

| 能力 | 实现 | 边界 |
|---|---|---|
| **配置描述文件设 DoH/DoT** | `.mobileconfig` + `DNSSettings` payload（iOS 14+） | 系统级，免 App、免开发者账号、零耗电。**iOS 唯一靠谱的路** |
| 个人 VPN 本地 DNS 过滤 | `NEPacketTunnelProvider` | 需 Apple 单独下发 Network Extension entitlement，个人申请多被拒；免费签名 7 天过期需重签 |
| （基本拿不到）DNS 代理 | `NEDNSProxyProvider` | 企业/MDM 专属 entitlement |

## 4. iOS：做不到什么

| 做不到 | 原因 |
|---|---|
| 跨 App 点「跳过」 | iOS 没有任何跨应用辅助功能 API。快捷指令只能「打开 App」，看不到也点不到别人的界面 |
| Safari 内容拦截器拦开屏 | 只作用于 Safari / SFSafariViewController / WKWebView 里的**网页**，对原生开屏零作用 |
| MITM 改包 | ATS + 证书固定 |
| 分应用 | 系统 DNS 设置是全局的，不能按 App 区分 |
| 免签名长期使用 | 免费账号 7 天过期，付费开发者账号 $99/年 |

**因此 iOS 交付的只能是「DNS 描述文件 + 明确的局限说明」，不承诺系统级拦截。**

> 已交付：`ios/SplashGuard-DNS-DoH.mobileconfig` / `-DoT.mobileconfig`，
> 生成器 `ios/make_profile.py`，校验脚本 `ios/check_profile.py`，
> 装法与能力边界见 `ios/README.md`。

## 5. 为什么普通插件 / 小程序根本不可能做到

1. **进程隔离**：Android 每个 App 独立 UID + SELinux 沙盒，iOS 每个 App 独立沙盒。第三方代码既读不到别人的网络包，也读不到别人的界面。
2. **小程序是宿主沙箱里的 JS**：没有系统网络栈、没有 Accessibility 权限、不能常驻、不能开机自启，连"在后台活着"都做不到。
3. **浏览器扩展只活在自己那个浏览器进程里**，管不到原生 App 的启动画面。

系统只开放了三个跨进程通道：**VPN（网络层）、无障碍（UI 层）、DNS 配置（解析层）**。
任何声称"能拦其他 App 原生开屏广告"的方案，必定落在这三者之内；不在其中的，要么在 root，
要么在骗人。

## 6. 三方案对比

| 维度 | A. 本地 VPN + DNS 过滤 | B. 系统私有 DNS (DoT) | C. 无障碍自动点跳过 |
|---|---|---|---|
| 所需权限 | 一次 VPN 授权，无 root | 无（改系统设置，需信任解析器） | 手动开无障碍，敏感权限 |
| 广告覆盖率 | 中（HTTPDNS 域名无效） | 中偏低（规则在远端、不能分应用） | 中（原生/WebView 命中高，自绘无效） |
| 稳定性 | 高（纯网络层，不怕 UI 改版） | 最高（系统原生） | 低（App 改 UI 就失效） |
| 耗电 | 极低（仅 DNS 报文进隧道） | 零 | 低（仅冷启动时扫描） |
| 上架难度 | 高（Play 易拒，国内商店基本不收） | 不涉及上架 | 极高（Play 严查无障碍滥用） |
| 法律/ToS 风险 | 中（需隐私政策，不碰付费内容） | 低（隐私交给解析器方） | 中高（误点广告即构成伪造点击） |
| MVP 定位 | **主体** | 零成本兜底模式 | 可选增强，默认关 |

## 7. 结论与选型

**A 为主体 + C 为可选增强 + B 作为降级模式。**

- A 是唯一「无视 App UI 改版、不用敏感权限、耗电接近 0」的长期可维护路线；
- C 只补 A 的盲区（HTTPDNS / 已缓存素材），但**只点击文本匹配「跳过/关闭」的控件**，
  绝不点广告区域本体——越界一步就是流量作弊；
- B 不写代码也能用，做成 App 内「一键跳转系统设置」的引导，作为不想开 VPN 时的降级模式。

### 诚实的覆盖率预期

不是 100%，也不是 80%。真实预期：

- 走系统 DNS 的中小 App 开屏广告：**大概率拦掉**
- 大厂 App 若启用 HTTPDNS：**DNS 层无效**，需靠无障碍点跳过
- 游戏类：**基本无效**
- 已缓存素材：**拦不掉**

这也正是为什么必须做「双通道」，而不是只做一个。
